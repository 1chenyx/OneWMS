# OneWMS 个性化仓库管理系统 · 设计蓝图

> 版本：v0.1（设计冻结稿）
> 日期：2026-10-30
> 状态：设计闭环，待动工

---

## 1. 愿景与需求

用户下载**一个应用**，通过自然语言告诉 AI 自己的仓储管理需求，AI 逐步将字段、流程、功能模块组装到位，形成完全个性化的 WMS。个性化配置可在设备间迁移，并在局域网/互联网内的所有节点保持同步。

### 1.1 原始需求与可行性结论

| # | 需求 | 可行性 | 难度 | 落点 |
|---|---|---|---|---|
| 1 | 单机直接运行 | 完全可行 | 低 | Tauri + SQLite，离线即普通软件 |
| 2 | 局域网/互联网通信 | 完全可行 | 中 | mDNS 直连 + 加密云中继 |
| 3 | 自然语言出入库 | 完全可行 | 中 | 工具总线 + Tool Calling |
| 4 | AI 组装个性化 | 可行但有边界 | **高** | 配置 DSL + 校验管线 + 人工确认 |
| 5 | 可迁移 | 完全可行 | 低 | 配置包 + 事件重放 |
| 6 | 配置全局同步 | 完全可行 | 中高 | oplog 统一管道 |

### 1.2 AI 组装的边界（必须向用户说明的物理限制）

- **配置组合**（约 80% 个性化需求）：隐藏字段、启用保质期预警、插入拣货阶段等——AI 生成配置 patch，完全可行。
- **全新功能**：AI **不能**凭空创造不存在的模块。需要插件（自研或市场下载，AI 可辅助编写但必须过沙箱与审核）。

## 2. 总体架构

三概念组合：

1. **本地优先（Local-first）**：每个节点都是完整系统，网络是增强不是依赖。
2. **插件化内核**：个性化是数据（配置），不是代码。
3. **AI 作为配置代理**：AI 不改程序，只生成配置；不碰 SQL，只走工具。

### 2.1 单节点内部结构

```
┌─────────────── 单节点应用（离线可用）───────────────┐
│  自然语言对话          表单/扫码界面（无 AI 也能用）  │
│      ↓                        ↓                     │
│  AI 编排层（意图→工具调用 · 需求→配置 DSL）           │
│      ↓                        ↓                     │
│  应用内核（模块注册表 | 流程引擎 | 工具总线）          │
│      ↓                                              │
│  可插拔领域模块（库存核心 | 批次 | 保质期 | 拣货 | …） │
│      ↓                                              │
│  SQLite（动态字段 JSON 列 + Oplog）                  │
│                         配置包 Profile（可导出迁移）  │
└─────────────────────────────────────────────────────┘
        ↓
  同步引擎（Oplog 交换 + 配置版本同步）
        ↓
  多节点网络（局域网直连 | 云中继 | 异地/移动端）
```

### 2.2 多节点网络

- **局域网**：mDNS 自动发现，节点直连。
- **互联网**：轻量云中继（自建 VPS），只转发加密消息，不存业务数据。
- **移动端**：局域网内手机浏览器/PWA 访问本机服务（可选能力，删除不影响系统完整性）。

## 3. 技术栈

### 3.1 决策：TypeScript 单语言全栈 + Tauri

| 层 | 选型 |
|---|---|
| 桌面壳 | Tauri（Rust 壳，系统 WebView，约 15MB，用户无需装环境） |
| 前端 | React/Vue + JSON Schema 动态表单 |
| 本地服务 | Node.js 内嵌于桌面进程（HTTP + WebSocket） |
| 数据 | SQLite（better-sqlite3） |
| AI | Vercel AI SDK（云 API / 本地 Ollama 无缝切换） |
| 同步 | oplog 自研（借鉴 Yjs 思路） |
| 插件 | MVP：动态 import + 权限清单；进阶：WASM（Extism） |

### 3.2 决策依据（四个硬约束）

1. **AI 工具调用是核心交互**：TS/Python 生态第一梯队（Vercel AI SDK、LangChain.js），provider 无关抽象现成。
2. **配置驱动动态 UI**：JSON Schema → Form 有现成方案（react-jsonschema-form、Formily）；原生栈需自研表单引擎。
3. **插件化 + 运行时动态性**：JS 动态 import + 沙箱成熟；WASM 是最正统的插件方案。
4. **多端覆盖**：Web 前端 + 本地 HTTP 服务 = 桌面/手机/平板一套前端。

补充：Rust 仅作 Tauri 壳模板，业务逻辑全在 TS；单语言的隐性收益——配置 DSL Schema、插件代码、前端逻辑统一在一套类型系统中，对「AI 组装」是实质加分。

## 4. 核心设计原则（系统宪法）

**一句话总结：一条事件管道、两条 AI 通道、三层配置、四个收敛单点。**

### 4.1 AI 权限模型：三层通道

| 层 | AI 能否触碰 | 通道 | 保护机制 |
|---|---|---|---|
| 代码 | 完全不碰 | — | — |
| 配置（Schema/流程/模块开关） | 能改 | 配置 DSL | JSON Schema 校验 → **人工确认** → 热应用 |
| 业务数据（单据/库存流水） | 能读写 | **仅限工具调用** | 工具内含业务校验（库存不为负、状态机合法） |

**AI 永远拿不到 SQL 执行权和 DDL 权限。** 它对数据的影响必须穿过工具函数，业务规则是绕不过的墙。

### 4.2 AI 的两条手

- **慢通道**：DSL 改配置——一律人工确认（用户决策：不搞信任分级）。
- **快通道**：Tool Calling 做业务——规则即护栏，不需逐次确认。

### 4.3 事件/命令分离纪律

- **事件**（过去时，事实）：只允许读 + 发布命令，**不允许直接写业务数据**。
- **命令**（祈使句，意图）：进队列，按 (优先级, 模块id) 确定顺序执行，照常过工具层校验。

### 4.4 四个收敛单点（权限口子的实体）

| 收敛点 | v1 形态 | 未来权限怎么加 |
|---|---|---|
| `resolveFieldView(field)` | 读 `visible` 布尔值 | 扩展为 `visible + roles` 联合判断，只改这一个函数 |
| 工具总线调用签名 | 每次调用带 `actor`（v1 只记日志） | 插入权限中间件；**AI 走同一条总线，权限对 AI 同样生效** |
| 流程条件求值器 | 只认模块开关/字段可见性 | 加 `permission:` 前缀条件类型（与流程表达式口子同组件） |
| oplog 事件 | 已带 `author`（LWW 裁决需要） | 权限审计免费获得历史数据 |

### 4.5 其他铁律

- **业务数据永不静默丢失**：任何卸载路径下，模块代码无权删除字段数据；只剩 owner 自己时弹窗问用户。
- **检测机械化，裁决人类化**：一切可机械判断的（类型、连通性、命名空间）自动检测；语义冲突（影响报告）交人确认。
- **确定性优先**：无法静态证明的组合，机制保证行为可预测（命令顺序确定、veto 保守合并），绝不随机。

## 5. 配置 DSL（Profile）

### 5.1 总结构

```json
{
  "profileId": "b3f1-...",
  "version": 42,
  "updatedBy": "node-A",
  "schema":     { "entities": { ... } },
  "workflows":  { "outbound": { ... } },
  "modules":    { "module.expiry": { ... } },
  "roles": { }
}
```

- **存全量快照，传增量 patch**（JSON Patch, RFC 6902）。
- `roles` 为预留空 key（v1 恒为空对象）。**向前兼容规则：老节点读到不认识的 key 一律忽略不报错**；oplog 事件带 `minVersion`，旧节点安全跳过。

### 5.2 字段层

```json
{
  "entities": {
    "sku": {
      "extensions": [
        { "key": "spec", "label": "规格", "type": "string",
          "visible": false, "providedBy": "core" },
        { "key": "expiry_date", "label": "保质期", "type": "date",
          "visible": true, "providedBy": "module.expiry" }
      ]
    }
  }
}
```

关键决策：

- **软删除**：「不要规格」= `visible: false`，不是物理删除。个性化配置同步/迁移不互相破坏。
- **全局字段注册表 + owner/usedBy 双层归属**（见 §7.1）：字段属于实体，不属于模块。
- **落库**：核心表固定列 + `ext_data` JSON 列，`json_extract()` 查询；字段标记「常用于查询」时才建表达式索引。
- **`visible` 未来语义扩展**：从布尔变为 `{ default, roles: {...} }` 时用新 key `visibleV2` 并存，永不改老语义。

### 5.3 流程层

```json
{
  "outbound": {
    "states": [
      { "id": "created", "label": "已创建" },
      { "id": "picking", "label": "拣货", "providedBy": "module.picking" },
      { "id": "packed",  "label": "打包" },
      { "id": "shipped", "label": "已发货" }
    ],
    "transitions": [
      { "from": "created", "to": "picking", "when": "module.picking.enabled" },
      { "from": "created", "to": "packed",  "when": "!module.picking.enabled" }
    ]
  }
}
```

- `when` 条件 v1 只允许引用**模块开关**和**字段可见性**——取值域全部在配置包内部，校验器可静态证明流程图连通（每个终态可达、无死锁）。
- **表达式口子已留**：条件求值器是独立可替换组件，未来加 `permission:` 前缀或小型表达式语言。

### 5.4 模块层

```json
{
  "module.expiry": {
    "enabled": true,
    "version": "1.2.0",
    "settings": {
      "warnDaysBefore": 30,
      "checkTime": "09:00",
      "notify": ["dashboard"]
    }
  }
}
```

- `settings` 的 schema 由模块 manifest 自带；校验、表单渲染、AI 上下文三件事共用一份 JSON Schema。
- 角色未来与模块同构（开关 + 参数 + AI 可编辑 + 全网同步），权限上线时走同一条 DSL 管线。

## 6. 模块清单（Manifest）规范

### 6.1 全景示例（保质期模块）

```json
{
  "id": "module.expiry",
  "name": "保质期预警",
  "version": "1.2.0",
  "minCoreVersion": "0.3.0",
  "description": "为 SKU 和批次增加保质期字段，在临近过期时产生预警。适用于食品、药品、化妆品等有有效期管理的仓储场景。",
  "signature": null,

  "capabilities": ["db.read", "events.subscribe", "jobs.register"],

  "slot": null,

  "dependencies": {
    "modules": ["module.batch"]
  },

  "fields": {
    "provides": [
      { "entity": "batch", "key": "expiry_date", "type": "date",
        "sharing": "shared", "label": "到期日期",
        "description": "用于计算剩余有效天数" }
    ],
    "requires": []
  },

  "tools": [
    { "id": "expiry.list_warning", "label": "查询临期清单",
      "description": "列出 N 天内到期的库存批次，按剩余天数升序",
      "parameters": {
        "type": "object",
        "properties": { "days": { "type": "integer", "minimum": 1, "maximum": 365 } },
        "required": []
      },
      "permission": "read" }
  ],

  "events": {
    "subscribes": ["batch.created", "inventory.adjusted"],
    "publishes": ["expiry.warning_triggered"]
  },

  "rules": [],

  "workflows": {
    "contributes": {
      "inbound": {
        "states": [ { "id": "quality_check", "label": "质检" } ],
        "transitions": [
          { "from": "received", "to": "quality_check" },
          { "from": "quality_check", "to": "putaway" }
        ]
      }
    }
  },

  "settings": {
    "schema": {
      "type": "object",
      "properties": {
        "warnDaysBefore": { "type": "integer", "minimum": 1, "default": 30,
          "description": "提前多少天开始预警" },
        "checkTime": { "type": "string", "format": "time", "default": "09:00" },
        "notify": { "type": "array", "items": { "enum": ["dashboard", "popup"] },
          "default": ["dashboard"] }
      }
    }
  },

  "ui": {
    "dashboardWidgets": [ { "id": "expiry-widget", "component": "./ui/WarningCard" } ]
  },

  "jobs": [
    { "id": "daily-check", "cron": "0 9 * * *", "action": "expiry.checkAll" }
  ],

  "entry": "./dist/index.js"
}
```

### 6.2 能力分区与卸载逆操作

| 分区 | 作用 | 卸载时的逆操作 |
|---|---|---|
| `fields` | 注册扩展字段（provides/requires） | 按 owner/usedBy 溯源处理（§7.1） |
| `tools` | 暴露给 AI/界面/权限的操作 | 从工具总线摘除 |
| `events` | 订阅/发布事件 | 自动退订（模块间解耦联动） |
| `workflows.contributes` | 向流程贡献状态和转移 | 移除自己贡献的部分 |
| `rules` | 向校验点注入规则 | 反注册 |
| `settings` | 参数定义 + 默认值 | 保留用户数据，移除定义 |
| `ui` / `jobs` | 界面组件 / 定时任务 | 反注册 |

### 6.3 关键机制

- **description 是一等公民**：AI 组装的匹配逻辑 = 用户自然语言 ↔ 模块/工具 description。工具 description 原文注入 function calling，措辞必须精确。
- **contributes 机制**：模块永不替换流程，只做贡献。流程 = 内核基础 + 各启用模块贡献叠加。同 id 状态冲突安装时拒绝。
- **capabilities 沙箱**：模块代码按最小授权供给（只声明了 `db.read` 就拿不到写接口）。安装第一屏呈现权限申请（手机装 App 心智）。**AI 被工具边界管住、模块被 capabilities 管住、用户（未来）被角色管住——三个执行体同一权限模型。**
- **事件命名空间**：`模块.事件名` 格式；只有 owner 模块能 publish 自己前缀的事件，订阅自由。

### 6.4 三个消费闭环

```
① 安装/卸载：注册表读 manifest → 注册到 Profile → version+1 → 广播
② AI 上下文：System Prompt = 当前 Profile 摘要 + 已启用模块的
   (id + description + settings.schema + tools)
③ 校验器：依赖满足？参数合法？（范围来自 schema）流程连通？
```

迁移闭环：新节点导入配置包 → 按 `modules` 的 id+version 从插件仓库拉代码包（**校验签名后**才进沙箱）→ 重放 oplog → 与源节点一致。

## 7. 冲突治理

### 7.1 字段共享与冲突（数据层）

**全局字段注册表：**

```
entity.batch.expiry_date:
  type:   date
  owner:  module.expiry            // 创建者（先到先得）
  usedBy: [module.expiry, module.fifo, module.promotion]
```

- `provides`：字段不存在时创建（成为 owner）；`requires`：声明依赖 + 期望类型。
- 后装模块发现字段已存在 → 不重复创建，类型兼容校验，追加 usedBy。

| 冲突类型 | 检测方式 | 处理 |
|---|---|---|
| 类型冲突 | 安装时硬校验 | 拒绝安装，告知不兼容 |
| 无意撞名 | `sharing` 声明 | private 自动加模块前缀（`expiry_note`），机制消除撞名 |
| 有意共享、类型兼容 | 注册表合并 | 共享，usedBy 追加 |
| 语义不同类型相同 | 命名规范 | 共享字段用中性名，私有语义用前缀（文档纪律） |

**卸载语义**：owner 卸载时 usedBy 有别人 → 字段保留，所有权移交注册表；只剩自己 → 弹窗（隐藏保留 / 彻底删除）。

### 7.2 功能冲突（行为层）

四类形态与解法：

| 类型 | 例子 | 解法 | 检测时机 |
|---|---|---|---|
| 择一型 | FIFO vs 效期优先出库策略 | **策略槽 slot**：`"slot": {"name": "outbound.strategy"}`，一个槽恰好一个占位者，UI 呈现为切换而非叠加 | 配置时 |
| 对抗型 | 禁止负库存 vs 紧急放行 | **规则注入** `mode: veto / warn`；veto 保守合并（任一否决即否决）；豁免必须显式 `"overrides": [...]` 并高亮确认 | 安装时 |
| 打架型 | A、B 订阅同一事件做相反操作 | **事件/命令分离**（§4.3）：事件处理器只读+发命令，命令队列顺序确定 | 架构上消灭 |
| 循环型 | A 依赖 B，B 依赖 A | 依赖拓扑排序 | 安装时拒绝 |

### 7.3 终极兜底：影响报告 + 人工确认

所有检测出的交集/冲突汇总成影响报告，与 AI 改配置走同一个确认界面。示例：

```
启用 module.promotion 将：
  + 共享字段 batch.expiry_date（已存在，类型兼容 ✓）
  + 向出库流程贡献状态「促销冻结」（与现有 4 个状态无冲突 ✓）
  ⚠ 此模块将豁免「禁止负库存」规则，确认？
```

## 8. Oplog 事件目录

### 8.1 事件信封

```json
{
  "eventId": "uuid",
  "actor": "node-A",
  "lamport": 1024,
  "seq": 882,
  "type": "inventory.adjusted",
  "payload": { ... }
}
```

- **双时钟**：`seq` 本节点内单调递增（A 的事件只有 A 有权威副本，按 seq 分段拉取）；`lamport` 跨节点逻辑时钟（收到事件时 `lamport = max(本地, 远端) + 1`）。
- **全序 = (lamport, actorId 字典序)**——所有并发裁决的唯一依据，无需中央服务器。

### 8.2 事件目录 v1

| 类别 | 事件 | 一致性 | 说明 |
|---|---|---|---|
| 业务 | `sku.created` / `sku.updated` | 最终一致 | ext_data 整体携带，字段级 LWW |
| 业务 | `inventory.adjusted` | 最终一致 | **只有流水事件，没有「改库存」事件**——库存 = 期初 + Σ流水，永远是派生视图 |
| 业务 | `order.created` / `order.state_changed` | 最终一致 | 记录 from→to |
| 业务 | `batch.created` | 最终一致 | |
| 配置 | `config.change` | **强一致** | patch + profileVersion（严格 +1） |
| 生命周期 | `module.installed` / `module.uninstalled` | **强一致** | manifest 摘要 + 版本 |
| 预留 | `role.*` | — | v1 不产生，信封已兼容 |

**业务事件全部过去时**（`adjusted` 不是 `adjust`）：命令本地执行（过 veto、工具校验），成功后落事件；事件本身永远合法，重放不需重新裁决。

### 8.3 幂等重放与冲突队列

- `eventId` 唯一索引，重放前查重；`inventory.adjusted` 应用 = 追加流水行。
- **唯一真冲突**：同一单据并发状态转移（A: created→picking，B: created→canceled）。后到事件 `from` 与当前状态不匹配 → **进冲突队列，UI 人工裁决**。不自动合并，仓储数据宁可停下来等人。
- 字段并发编辑：全序 LWW，输的编辑留在事件历史可追溯，不弹窗。

### 8.4 配置强一致的机械化验证

`config.change` 的 profileVersion 严格 +1 形成链：收到 v43 但本地 v41 → 缺 v42 → 向源节点补齐；补不齐 → 全量拉 Profile。**配置收敛不靠信任，靠链条可验证**——版本链断裂立即可知，不存在静默丢失。

### 8.5 同步协议

```
① mDNS 发现 → 握手交换 (nodeId, profileVersion, 各节点 seq 水位)
② profileVersion 不一致 → 低者全量拉 Profile，立即收敛
③ 事件交换：按 actor 分通道，拉取缺失的 seq 区间
④ 应用：按 (lamport, actorId) 全序重放
⑤ 兜底：定期互发业务 checksum，不匹配 → 全量校验/重建
```

- **全量为真，增量为快**：增量只是加速，任何怀疑时刻可用全量重建（「修复同步」按钮 = 丢弃局部状态走全量重放）。
- 新节点加入 = ② + 全量事件重放（或快照 + 增量）。**迁移和同步是同一个动作的两种节奏。**
- 传输安全：payload 用工作区密钥端到端加密（导出配置包/接纳新节点时人工确认交换），信封明文供路由，中继只见密文。

### 8.6 节点分层与部分副本（公司场景）

**问题**：公司级数据量（百万级事件、数十万 SKU）下，每个员工节点同步全量事件流不现实。

**关键切分：账本全量 ≠ 数据分发全量。** 全量重放是锚点节点的特权，不是每个节点的义务：

```
种子节点（服务器/主机）   存全量事件流 + 全部派生视图，事件排序权威
员工电脑（部分副本）      快照引导 + 订阅范围数据 + 离线队列
PDA/手机（最小副本）      只订阅本仓库单据 + 扫码所需最小集
```

- **订阅机制**（filtered replication 模式）：客户端声明 `{ entities, filter, since }`，服务端按需推送增量。
- **快照引导**：新客户端从「当前派生视图快照 + 后续增量事件」启动，不重放历史账本。
- **不变的**：事件信封、提交协议、离线队列、配置全量同步——客户端照旧本地攒事件、上线提交排序。
- **两种部署模式，同一架构的配比差异**：
  - 模式 A（个人/小团队）：对等全量节点，快照是可选优化；
  - 模式 B（公司）：种子节点 + 部分副本，快照是客户端引导必需品。
- 量级参考：百万事件账本 ≈ 400MB（仅锚点存）；员工快照几十 MB；PDA 几 MB；日增量几百 KB。

### 8.7 客户端形态光谱（中心化后本地库的角色）

**判定法则：要不要离线能力，决定要不要本地库；「以谁为准」只决定数据权威归属，不决定客户端要不要缓存。**

```
模式 A  本地全量节点    本地 = 完整账本 + 全部投影（个人/小团队）
模式 B  缓存 + 发件箱   本地 = 订阅投影快照 + 离线事件队列（公司员工端）
模式 C  瘦客户端       本地 = 内存缓存，断网即停（纯在线 Web/管理后台）
```

- 模式 B 的本地 SQLite 存的不是账本：**投影快照**是缓存（服务器可随时重建）；**发件箱**是待提交事件队列（结构上仍是 oplog）。
- **WMS 领域离线是刚需**：仓库 WiFi 盲区/漫游断连是常态，扫码操作不能因断网停工——断网期间的操作只有「排队上交」一条合理出路，排队就需要本地存储。
- 三种客户端对接同一服务器、同一套协议，差别只是订阅范围大小和离线容忍度（§8.6 订阅机制的两个参数），不存在选型后重写。

### 8.8 传输层：全场景 WebSocket + 一套应用层协议

| 场景 | 发现 | 传输 |
|---|---|---|
| 局域网 | mDNS 广播（`_onewms._tcp.local`，零配置） | `ws://IP:7800` 直连 |
| 互联网 | 中继在线目录 | `wss://relay` 中继转发 |
| 互联网 P2P（可选优化） | WebRTC 信令 | 打洞成功直连，失败回退中继 |

- **中继极薄**：只做在线目录 + 密文转发；流量小（日增量几百 KB），成本≈零。E2E 加密下中继无需被信任。
- **加密双层**：传输层 wss（TLS）+ 应用层 payload 永远工作区密钥加密（信封明文供路由）。信任锚在用户密钥，不在基础设施。
- **消息目录（全场景同一套）**：hello（握手/水位）、pull-events / events（区间拉取）、push-events / ack（发件箱提交）、subscribe / snapshot / notify（订阅分发）、heartbeat（心跳 + checksum 兜底）。
- **WebSocket 的选择理由**：浏览器唯一原生双向通道——一套协议同时服务桌面节点与未来 PWA 瘦客户端；裸 TCP 浏览器不可用，HTTP 轮询延迟高，MQTT 引入 broker 依赖而用不上其规模优势。快照大文件走 HTTP 分页下载（可断点续传），WebSocket 管实时增量。
- **断线策略**：指数退避重连 + 发件箱自动补投 + 序号续传（从上次水位继续）。

## 13. 架构演进：未来中心化服务器路径

**结论：从对等网迁移到「服务器数据为准」是顺流而下，因为本方案选择了事件溯源（oplog）——事件模型拓扑无关，变化的只是事件的排序权归属。**

### 13.1 去中心化机制 → 中心化对应物

| 现在（对等网） | 未来（服务器为准） | 变化性质 |
|---|---|---|
| lamport 双时钟 + (lamport, actorId) 全序 | 服务器分配全局序号 | 简化：单计数器替代分布式时钟 |
| 字段并发 LWW 自动合并 | 服务器接收顺序即裁决 | 简化：单点排序天然无并发 |
| 冲突队列 + 人工裁决 | 提交时服务器实时拒绝 | 简化：冲突当场暴露 |
| 按 actor 分通道交换 seq 区间 | 节点推本地队列 → 服务器排序 → 回发 | 同一机制换视角（离线队列 + 服务器对账） |

「本地 oplog + 同步交换」与「离线队列 + 服务器对账」本质同构：节点离线时本地攒事件，上线后提交权威排序。现有同步协议几乎无需重写。

**反面参照**：若当初选 CRDT 状态合并（Yjs 类），其合并语义与无权威模型绑死，迁移到「服务器说了算」非常痛苦。本方案未选 CRDT，方向正确。

### 13.2 数据库分层策略

- **节点端：SQLite 永远够。** 中心化后节点退化为「缓存 + 离线队列」角色。
- **服务器端：两步走。** 初期（几个节点/个人团队）服务器也用 SQLite + WAL；到多租户 SaaS 规模换 PostgreSQL——因事件模型，换引擎 = 导出事件流 → 新库重放，业务视图（库存 = Σ流水）自动重建。是「重放」不是「数据库搬迁」。
- **水平扩展路径：按 workspace 分片。** 关键洞察——事件全序只在同步组（工作区）内需要，跨工作区事件永不排序（密钥都不共享）。因此按 workspaceId 分片 = 无限水平扩展路径：一个工作区一个分片，热点独占资源，冷区打包归档。跨工作区全序是许多系统被数据库拖死的隐含假设，本事件模型从第一天即无此假设。
- **多租户前置条件（v1 即做）**：事件信封显式携带 `workspaceId`（已隐含在同步协议加密边界中，需显式成字段）。多租户此后 = 表加一列 + 查询加一个 where，而非改造。

### 13.3 渐进渗透路径（无「大迁移日」）

```
现有同步协议加角色位：节点握手声明 "authority": true
→ config.change / 冲突裁决类事件优先路由给权威节点
→ 其他节点逐步让渡「自行排序」
→ 每一步系统都完整可用
```

### 13.4 从第一天守住的纪律（迁移成本为零的前提）

1. **事件不可变**：修正 = 追加补偿事件，绝不编辑已发布事件（append-only，现有设计）。
2. **全程 UUID**：eventId 已是 uuid；业务主键（sku、单据号）同样禁用数据库自增 int——自增 ID 是中心化迁移经典天坑，须写入开发规范。
3. **不依赖单写者假设**：业务规则全部在工具层校验，不依赖「只有一个人写」的隐含前提。

### 13.5 SaaS 化路径（预留口子，实现后置）

**定位：SaaS = 种子节点（§8.6）× N 个工作区 + 账号计费层。** 工作区天然就是租户，不发明新的隔离概念。

```
SaaS 服务端
  ├─ 网关（TLS、认证、限流）              ← 新增，标准件
  ├─ 账号服务（注册/登录/订阅/计费）        ← 新增，标准件
  ├─ 租户管理（建工作区/成员/配额）         ← 新增，标准件
  └─ 每个工作区：事件流 + 投影 + 订阅分发    ← 即 §8.6 种子节点，一租户一个
       ↑                        ↑
  桌面客户端（模式B）        浏览器用户（模式C）
```

**架构复用清单（零新概念）**：租户隔离 = workspaceId + 密钥边界；水平扩展 = 按 workspace 分片（§13.2）；Web 端 = 模式 C 瘦客户端 + WebSocket（§8.7/8.8）；每租户个性化 = Profile 工作区级独立同步（§5）；每租户 AI = 客户端跑、各租户自配 key（§9）；数据库演进 = SQLite → PG 按租户分区（§13.2）。新增部分（账号/支付/租户后台/运维）均为产品层标准件，架构层零改动。

**两个架构红利**：
1. **零知识 SaaS**：事件 payload 按工作区密钥加密、密钥在租户手里，平台运营商看不到租户业务数据；AI 在客户端跑，不需要服务端读明文——隐私承诺与 SaaS 功能不冲突。
2. **多工作区并存**：同一客户端可同时加入「本地单机工作区」与「云端 SaaS 工作区」，一个 App 内切换——个人数据留本机、公司数据在云端。

**演进路径（三级形态共用同一客户端/协议/事件模型）**：

```
v1     个人/单机      对等局域网同步           ← 里程碑 1–5
v1.x   公司私有部署    种子节点 + 部分副本       ← §8.6/8.7
v2     SaaS          种子节点 × N + 账号计费    ← 本节，产品层工程
```

**v1 即守的口子（只为不堵死，不实现）**：
1. `workspaceId` 进事件信封（§13.2 已定）。
2. **运行时上下文带「当前工作区」参数**：内核 API（工具总线、字段注册表、事件写入）以工作区为第一参数，不硬编码「单工作区进程」假设。
3. **actor 字段语义开放**：v1 是节点 id，未来可平滑升级为「用户身份」（账号体系上线后），事件历史无需迁移。
4. **客户端连接层支持多服务器配置**：本地服务 / 中继 / SaaS 网关只是 URL 差异（§8.8），不写死「只连本机」。
